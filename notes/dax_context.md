## 0. 一句话定位

> **一个度量值 = 一条写了聚合、但没写 `WHERE` 和 `GROUP BY` 的 SQL。那两样由用户来补。**

```dax
Total Amount = SUM ( fact_sales[amount_rmb] )
```

它**从来不是**"全表总和"。它永远带着一个看不见的 `WHERE` —— 那个 `WHERE` 就是**筛选上下文**。

同一个度量值放进不同的视觉对象，会被算很多次，每次的 `WHERE` 都不一样。**排错时先问"它现在的 WHERE 是什么"，而不是先读公式。**公式往往没错，错的是环境。

---

## 1. 两种上下文

### 筛选上下文（filter context）

**这个数字被计算的那一刻，当前生效的所有筛选条件的集合。**

它从**外面**来，度量值被动接收：

| 来源 | 例子 |
|---|---|
| 视觉对象的行 / 列 | 矩阵里的 `region = 华东` |
| 切片器 | 用户勾了"钢厂" |
| 筛选器窗格（视觉 / 页面 / 报表级） | |
| **RLS** | **用户看不见，但在最外层**，先于一切生效 |
| `CALCULATE` | 公式自己加的 |

两条性质：

1. **分组这件事本身就是筛选上下文。**`SUMMARIZECOLUMNS(dim_date[year], …)` 为每个年份建立一个筛选上下文，再在每个里面各算一遍。
2. **沿关系箭头传播**，单向：维度表 → 事实表。

### 行上下文（row context）

**"当前正在处理的是哪一行。"**

只存在于两个地方：**计算列**、**迭代器内部**（`SUMX` / `AVERAGEX` / `FILTER` / `MAXX` …）。

⚠️ **行上下文不跨关系传播。**在 `dim_customer` 上写 `fact_sales[amount_rmb]` 会报
`A single value for column 'amount_rmb' cannot be determined` —— 因为一个客户对应上百行成交（华东特钢 161 行），"哪一行"没有答案。

### 两者的组合决定结果

| | 行上下文 | 筛选上下文 | 结果 |
|---|---|---|---|
| 计算列 `SUM(fact_sales[amount_rmb])` | 有 | **空** | 每行都是 27,106,012,244.79 |
| 计算列 `CALCULATE(SUM(…))` | 有 | 转换出来的 | 每行是该客户自己的金额 |
| **度量值**放进分组查询 | **没有** | 有（分组给的） | 每组一个数 ✅ |

## 2. 上下文转换（context transition）

> **行上下文不会自动变成筛选上下文。`CALCULATE` 会把它转换过去。**

```dax
test_calc = CALCULATE ( SUM ( fact_sales[amount_rmb] ) )   -- 一个筛选参数都没写
```

建在 `dim_customer` 上，每行变成该客户自己的金额（华东特钢 2,197,988,584.16）。

**只要在行上下文里引用一个度量值，就自动发生一次上下文转换**——不用你写 `CALCULATE`，它就在那儿。这是 DAX 最隐蔽的机制。

两个后果：

- ✅ **有用**：`AVERAGEX ( VALUES ( dim_date[Date] ), [Total Stock] )` 能逐日算出库存，靠的就是它。
- ⚠️ **慢**：`FILTER ( fact_sales, [Total Amount] > x )` 会对 1,843 行各触发一次。**能用列就用列**（性能）；**需要逐行重算一个度量值时，用度量值才是对的**。

## 3. `CALCULATE` 的两个作用

```dax
CALCULATE ( 表达式 , 筛选器1 , 筛选器2 , … )
```

| | 作用 |
|---|---|
| ① | 按写的条件**改写筛选上下文** |
| ② | **只要有行上下文就自动做上下文转换**，哪怕一个参数都不写 |

### 筛选器怎么组合

| 情况 | 行为 |
|---|---|
| **筛选器之间** | **取交集**（AND） |
| 筛选器 vs 外部上下文，**在它点名的列上** | **替换** |
| 外部上下文里**没被点名的列** | **保留** |

"替换"的机制是语法糖展开出来的：

```dax
CALCULATE ( …, fact_sales[tonnes_wet] >= 30000 )
≡ CALCULATE ( …, FILTER ( ALL ( fact_sales[tonnes_wet] ), fact_sales[tonnes_wet] >= 30000 ) )
```

**先清空那一列，再套新条件** —— 所以是替换不是叠加。

也正因为筛选参数**本质只接受一张表**，跨列条件（"金额 ÷ 干吨 > 1000"）必须自己写 `FILTER`。

### ⭐ 点名的列越多，度量值越"固执"

`Steel Amount` 在年×类型六行里两年不同（年份没被动）；`Steel Amount 2026` 六行全一样（两列都被替换）。
**把 `year = 2026` 写死进度量值，用户点切片器数字纹丝不动——看的人会以为报表坏了。**

### 空 `CALCULATE`

`CALCULATE(表达式)` 不带筛选参数时只剩作用 ②。**度量值里没有行上下文，所以它什么也不做。**
判断法：**`CALCULATE` 后面有没有逗号？**没有逗号的，在度量值里一定是多余的。

## 4. 清除半径（`ALL` 家族）

| 写法 | 清掉谁 |
|---|---|
| `ALL ( 表[列] )` | **一列** |
| `ALL ( 表 )` | **一整张表的所有列** |
| `ALL ( fact_sales )` | 事实表 **＋ 所有通过关系挂上去的维度表**（含日期）← 比直觉大得多 |
| `ALLSELECTED ()` | 只清**视觉对象内部**的筛选，**保留外部**（切片器） |
| `ALLEXCEPT ( 表, 保留列… )` | `ALL` 的逆：**保留**点名的，清掉其余 |
| `VALUES ( 表[列] )` | **不清**。返回当前还看得见的值（`ALL` 的反义词） |

**规律：点名得越具体，清得越少。**读别人的度量值，看到 `ALL` 第一件事就是问"清除半径有多大"。

### `ALL(一列)` 是相对的，`ALLEXCEPT` 是绝对的

`ALL ( dim_customer[customer_type] )` 声明的是"清掉什么"，所以报表加一层分组，它的行为就变。
`ALLEXCEPT ( dim_customer, dim_customer[region] )` 声明的是"保留什么"，加多少层都不变。

实测：矩阵里加一层 `customer_type`，同一个度量值从 **14.00%** 变成 **27.81%**，不报错。
**要固定分母，用 `ALLEXCEPT`。**

### 时间智能函数的清除范围不一样

> ⭐ **时间智能函数（`SAMEPERIODLASTYEAR` / `DATESINPERIOD` / `DATESYTD` …）当 `CALCULATE` 的筛选参数时，清除的是整张日期表上的筛选，不只是 `Date` 那一列。**前提是这张表 **Mark as date table**。

这就是为什么 `CALCULATE([Total Amount], DATESINPERIOD(…, -3, MONTH))` 在"2026 年 1 月"这一行能跨到 2025-11、2025-12 —— 外层的 `year = 2026`、`month = 1` 一起被清掉了。

**普通筛选器只清它点名的那一列。**这个差别踩过一次：把 `CALCULATETABLE` 放进 `AVERAGEX` 里面，外层的 `month` 没被清，上下文转换出来的 `year_month` 和它打架，结果每一行都等于当月金额。

**判断要不要先清：你是要"走出"当前格子，还是"细分"当前格子？**
走出去（当前月 → 前三个月）必须清；留在里面细分（当前月 → 这个月的每一天）不用清。

## 5. 层级感知

### `VALUES` 的那座桥

`VALUES(列)` 返回**一张表**。**只剩一行一列时，DAX 自动把它当标量用**；降不了格就报错——而且是**整个视觉对象**报 "Error fetching data"，不是单格报错。

三个函数建立在这上面：

| 函数 | 问什么 |
|---|---|
| `HASONEVALUE ( 列 )` | 这一列**是不是只剩一个值** |
| `SELECTEDVALUE ( 列, 兜底 )` | 只剩一个就给我那个值 ≡ `IF(HASONEVALUE, VALUES, 兜底)` |
| `ISINSCOPE ( 列 )` | 这一列**是不是当前这一行的分组依据** |

### ⭐ `HASONEVALUE` vs `ISINSCOPE`

| 场景 | `HASONEVALUE` | `ISINSCOPE` |
|---|---|---|
| 该列在行区分组 | True | True |
| 小计行，组里有 8 个值 | False | False |
| **小计行，组里只剩 1 个值** | **True** ✗ | **False** ✅ |
| **该列不在行区，但切片器只选了一个** | **True** ✗ | **False** ✅ |

**判断层级用 `ISINSCOPE`；判断唯一值、取值用 `HASONEVALUE` / `SELECTEDVALUE`。**

不是谁更准——**Card 没有分组层级，`ISINSCOPE` 在它上面永远 FALSE**，动态标题只能用 `SELECTEDVALUE`。

⚠️ 用 `HASONEVALUE` 判断层级，bug **依赖数据分布和用户行为**：每个区域都有两个以上客户时它永远正确，直到某天某区只剩一个客户、或用户点了单个客户。**报表会在交付半年后自己坏掉。**

### `SELECTEDVALUE` 是个转折点

此前所有度量值都只是**被动接收**筛选上下文。`SELECTEDVALUE` 是第一个让度量值**主动读取用户选择**的函数。两类用途：① 动态标题；② **假设分析**（参数表 + `SELECTEDVALUE` 把滑块值喂进公式）。

⚠️ 兜底文案的含义是"**不止一个值**"，不是"全部"——写成"全部区域"在部分筛选时就是在撒谎。

### 总计行不是上面各行的加总

**度量值没有"总计行"这个概念**，它只是在一个更宽的筛选上下文里又算了一次。
占比六行加起来 200%、总计显示 100%；`DISTINCTCOUNT` 在总计行去重；加权均价在总计行是"总金额 ÷ 总吨数"。**全都是对的，错的是"总计 = 上面相加"这个预期。**

## 6. 时间智能：一个机制

> **某个函数造出一张日期表 → `CALCULATE` 拿它当筛选器。**

记住这一条，十几个函数都是变体：

| 函数 | 造出什么 |
|---|---|
| `SAMEPERIODLASTYEAR ( d )` | 当前范围整体平移一年 ≡ `DATEADD ( d, -1, YEAR )` |
| `DATEADD ( d, n, 单位 )` | 通用版：DAY / MONTH / QUARTER / YEAR |
| `TOTALYTD ( 表达式, d )` | ≡ `CALCULATE ( 表达式, DATESYTD ( d ) )` |
| `DATESINPERIOD ( d, 起点, n, 单位 )` | 从起点数 n 个单位的连续日期 |
| `CLOSINGBALANCEMONTH ( 表达式, d )` | ≡ `CALCULATE ( 表达式, ENDOFMONTH ( d ) )` |
| `LASTNONBLANK ( 列, 表达式 )` | 最后一个让表达式非空的值（单行表） |

**为什么不能用 `CALCULATE` 写死**：同比的条件是**相对于当前这一格**的，20 行就要写 20 个度量值。对应 SQL 的 `LAG(x, 12) OVER (…)` —— 相对位置，不是绝对值。

### 为什么 `dim_date` 要建成整年 730 行 + Mark as date table

日期**连续无缺口**（平移后落在缺口上不报错但算不全）、**覆盖整年**（`TOTALYTD` 从 1 月 1 日起算）、**已标记**（引擎才知道哪张是日历）。

⚠️ **永远用 `dim_date[Date]`，不用 `fact_sales[sale_date]`**——后者有重复、有缺口。
⚠️ **时间计算走真实日期列，不走数字月份**：`month − 1` 在 1 月变成 0；`DATEADD` 跨年是自然行为。

### 指标能不能跨层级，看它有没有写死时间单位

| 指标 | 时间单位 | 跨层级 |
|---|---|---|
| `MoM %` | 写死 `MONTH` | ❌ 只有月层有意义 → 加 `ISINSCOPE` 护栏 |
| `YoY %` | 写死 `YEAR` | 🟡 月 / 季都对，**年度行要截断口径** |
| `Closing Stock` | **没写死**（"最后一个有数据的那天"） | ✅ 月末 / 年末 / 最新都成立 |

`CLOSINGBALANCEMONTH` 名字里就带着 **MONTH** —— **名字已经告诉了你它的适用层级。**

### 年度行那个 −32.11%

`dim_date` 是整年，引擎按**日历**算而不是按**有没有数据**算。于是 2026 年度行拿 **8 个月的实绩** 比 2025 的 **12 个月**：

| 口径 | 2026 vs 2025 |
|---|---|
| 年度行默认显示 | **−32.11%** |
| 诚实的比较（1–8 月 vs 1–8 月） | **+0.40%** |

修法：`VAR` 把"最后一笔成交是哪天"冻住，再用 `EDATE(…, -12)` 截断去年的日期范围。

## 7. `VAR`

```dax
VAR a = …          -- 只能引用前面定义的（同 SQL 的 CTE）
RETURN 表达式       -- 必须有
```

三个用途：**可读性**、**性能**（重复引用只算一次）、⭐ **冻结**。

### 冻结

> **`VAR` 在定义那一刻求值，之后 `CALCULATE` 改筛选也影响不了它。**

```dax
VAR x = [Total Amount]
RETURN CALCULATE ( x, dim_customer[customer_type] = "钢厂" )
```

在"贸易商"行返回的是**贸易商自己的金额**——到第二步时公式实际是 `CALCULATE ( 10590912415.77, 钢厂 )`，常数，`CALCULATE` 无事可做。**那个 `CALCULATE` 完全是废的，而且不报错。**

**但"冻结"不等于"无视筛选"**：`VAR` **完整接收定义那一刻已经存在的**筛选上下文，只是收不到**之后**的改动。要无视筛选必须自己写 `CALCULATE ( …, ALL ( … ) )`。

双刃：想让 `CALCULATE` 影响某个值 → **不能**提前存进 `VAR`；想让某个值在每一行都一样 → **正要**存进 `VAR`。

**调试手法**：把变量单独建成一个度量值，看它在每一行算出什么。藏在公式里看不见，拆出来就看得见。

**存什么**：先问"这个公式里哪个东西我用了不止一次"——存那个，不是存算到一半的中间结果。

## 8. 半可加

| 类型 | 能否沿时间相加 | 例子 |
|---|---|---|
| 可加 | ✅ | 销售额、吨数、笔数 |
| **半可加** | ❌ **时间上不能**，其他维度能 | **库存**、账户余额、人数 |
| 不可加 | ❌ 都不能 | 单价、水分率、汇率 |

库存是**存量**：8 个港口可以相加（空间可加），1 月份 5 个周五不能相加（时间不可加）——那是同一批矿数了 5 次。
CFA 对照：**利润表是流量，资产负债表是存量。**

实测：直接 SUM，Total 行 **23.39 亿吨**，真实值约 2,650 万吨 —— **大 88 倍，不报错。**

### `CLOSINGBALANCEMONTH` 的隐含前提

它筛**日历上那个月的最后一天**，从不问"那天有没有数据"。本项目快照是**每周五**，20 个月里只有 4 次月末恰好是周五 → **命中率 20%，其余全空白**。

> **这套函数是为"每日余额"设计的**（银行余额、每日结存）。
> **函数名听起来正合适，不等于它适合你的数据粒度。**遇到大面积空白，第一个问题不是"公式错了吗"，而是"**这个函数对我的数据粒度做了什么假设**"。

正解：`CALCULATE ( [Total Stock], LASTNONBLANK ( dim_date[Date], [Total Stock] ) )`。

## 9. ⭐ 不报错但口径错 —— 全清单

模块 4 撞到的全部。**到岗后真正会出事的就是这一类。**

| # | 错法 | 长相 |
|---|---|---|
| 1 | 比率写成计算列 | "平均数的平均数"，差 1 元/吨 ≈ 1,500 万 |
| 2 | 双向筛选 | 把一个**显眼**的错（五人全 14）换成一个**隐蔽**的错（13/14，看着合理） |
| 3 | 给整数列加引号 | DAX 自动转换，**结果正确**——比报错更危险 |
| 4 | 格式字符串 ≠ 值 | 0.12% 未设格式显示成 **0**，像是孤儿已清干净 |
| 5 | `ALL` 的清除半径搞错 | 换个列分组就失效；`ALL(事实表)` 连日期一起清 |
| 6 | `ALL(一列)` 当固定分母 | 加一层分组，14.00% → 27.81% |
| 7 | **复用为别的用途写的度量值** | 明细行全错、**总计行碰巧正确**（盯总计对账会漏掉） |
| 8 | `列 <> BLANK()` 当判断空 | DAX 里 `BLANK() = 0` 成立，会把真正录了 0 的行排除 |
| 9 | 筛选条件**恒为真** | 等于没筛，结果和原来一模一样 |
| 10 | `VALUES(维度表[列])` 当"做过生意的" | 五个数各不相同、都合理、**看不出错** |
| 11 | BLANK 的不对称 | 分子按 0、分母算全额 —— **是 DAX 替你决定的** |
| 12 | 分子分母口径不一致 | 无主的钱被摊到 13 个真客户头上 |
| 13 | `HASONEVALUE` 当"在不在这一层" | 小计行显示 100%；**依赖数据分布，半年后才暴露** |
| 14 | 写死年份的练习品被误用 | 一半正确、一半全错 |
| 15 | 未来月份 −100% | 像业务归零 |
| 16 | 护栏判断了**派生指标** | 累计值永远不空 = 等于没护栏 |
| 17 | 年度同比 8 个月比 12 个月 | −32.11% vs +0.40% |
| 18 | 跨两年看"总计行同比" | +148.29%，或环比的 **0.00%**（恒等式，**漂亮的整数最容易骗人**） |
| 19 | 按 `month` 分组忘了 `year` | 两年同月被加在一起 |
| 20 | 半可加直接 SUM | 大 88 倍 |

### ⭐ 一个指标，三张排名

同一个"人均客户金额"，三种口径都不报错、都"算对了"，**王磊在第一张表里被降两名，理由只是他经手过两笔客户编号没对上的单子**。

**到岗后能保护你的只有两件事：把口径写进名字，去问这个数要拿来干什么。**

### 写下真正的规则，不要写死今天的巧合

| 问题问的是 | 真正的条件 | 代理条件（今天碰巧等价） |
|---|---|---|
| 这笔单**没有账期数据** | `ISBLANK ( credit_days )` | ~~`customer_id = -1`~~ |
| 这笔单的**客户无法识别** | `customer_key = -1` ✅ | ~~`customer_type = "未知"`~~ |

区别在于 **-1 是碰巧重合，还是概念本身的编码**。
同一原则贯穿整个项目：按列名删列（不按 `Column10`）· 孤儿按"匹配不上"归 -1（不按"替换 999"）· 删掉 `Columns=12` · 滚动均值的分母不写死 `3`。

## 10. 到岗后的排错清单

打开一个算得不对的度量值，按这个顺序问：

1. **它现在的筛选上下文是什么？**（不是先读公式——公式往往没错）
   有没有没注意到的页面级筛选器？**RLS 在不在最外层？**
2. **这个数在哪一层？**月行 / 小计行 / 总计行的口径一样吗？
3. **`ALL` 的清除半径多大？**时间智能函数清的是整张日期表。
4. **有没有写死的东西？**年份、列数、分母、位置——今天碰巧对不代表下个月对。
5. **分子和分母的筛选条件一样吗？**
6. **BLANK 在哪一侧？**分子按 0、分母算全额这种不对称，是引擎替你做的决定。
7. **名字和公式对得上吗？**`Amount % of Total` 的 "Total" 指哪个 total？
8. 整个视觉对象空白 → 某个度量值在某一层算不出来。**度量值一个个拿掉**，点开 `See details` 读报错。

### 以及一条流程上的

**在聊天 / 邮件 / 文档里写对，不等于模型里改对。**改完一定回视觉对象看数字变了没有——`Amount % of Region` 曾经在模型里错了三天，靠的是两次记录对不上才发现的。

**指标不是写出来的，是对账对出来的。**
