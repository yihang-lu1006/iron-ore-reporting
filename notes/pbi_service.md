# Power BI Service + RLS 笔记（模块 2c）

> 2026-11-12 · 模型：`powerbi/Yihang_Lu_IronOre_Model.pbix` · 工作区：`BHP Prep`
> 目标不是学管理员，是**到岗第一周打开别人的工作区时能看懂眼前是什么**。

---

## 1. 四个容易混的名词

| 名词 | 是什么 | 类比 |
|---|---|---|
| **工作区 Workspace** | 开发者干活的地方，放模型和报表 | 办公室 |
| **语义模型 Semantic model** | 数据副本 + 表 + 关系 + 度量值（= `.pbix` 里的 DataModel） | 厨房和食材 |
| **报表 Report** | 页面和图表，连到**某一个**语义模型 | 菜单 |
| **App** | 打包发给使用者的东西 | 对外营业的餐厅 |

### 三条关键关系

1. **一个语义模型可以挂多个报表。** 销售一个报表、财务另一个，连同一个模型 → 数据只存一份、口径只有一套、刷新一次全部更新。反过来说：**改一次模型，所有挂在上面的报表一起变。**
2. **把人加进工作区 ≠ 把 App 分享给人。** 前者给的是**改**的权限，后者只是**看**。
   > 到岗后如果发现全组都是工作区的 Member，意味着所有人都能改生产报表——这是一个一句话能说清、也很容易修的治理问题。
3. **发布一个 `.pbix`，云端会拆成两个条目**：Semantic model + Report。所以**刷新计划配在语义模型上，不是报表上**——数据在模型里，报表只是画面。

### 为什么不用 My Workspace

个人空间**不能分享、不能发布 App**，东西放那儿等于没人能接手。到岗后看到重要报表躺在某人的 My Workspace 里，本身就是个治理问题。

## 2. Gateway（本地数据网关）

### 判断题与答案

> **Q：数据源是本地 CSV（`C:\Users\...\data\`）时，Power BI 云端要怎样才能读到？**
>
> **A：读不到，必须在本地装 On-premises data gateway。**
> 云端没有权限访问我的硬盘；但也不是"没有办法"——如果真没办法，所有报表就只能留在存数据的那台电脑上，云服务失去意义。

> **Q：模块 3 把数据源换成 Snowflake 之后，还需要网关吗？**
>
> **A：不需要。** 网关解决的是"**云端够不到的地方**"。Snowflake 本身就在云上，Power BI 可以直接连它，中间不需要任何人代为转达。
>
> **判断标准一句话：数据源在不在云上。** 在云上（Snowflake、SharePoint Online、OneDrive for Business、Azure SQL）→ 不需要；在本机、公司内网、本地服务器 → 需要。

### 网关的工作方式（和直觉相反的地方）

不是云端主动来连你的电脑——那样防火墙必须开一个入站口子，企业 IT 不会同意。

实际是**反过来**：网关装在本地，由**它主动向外**连到 Power BI 云端并保持长连接。到了刷新时间，云端沿这条**已经建立好的**连接发指令，网关在本地读文件、处理好再传回去。

```
云端 Power BI  ◀──── 网关主动建立的连接 ────  本地（网关 + 数据源）
```

**所以防火墙不用开任何入站端口**——这是企业能用它的原因。

两个推论：
1. 刷新时那台机器必须开着、网关服务在运行。
2. 分**个人模式**（只服务自己，装起来最简单）和**标准模式**（多人、多数据源共用，企业用这个）。

### 为什么这次没装

网关的安装和维护在公司是 IT 的事，而个人模式也复现不了企业环境的故障模式（网关集群掉线、服务账号密码过期）。**不会去管理它，但会被它卡住**——所以要会的是下面三件事，而不是安装。

### 不装也必须会的三件事

1. **认出它属于哪一层。** "You have no personal gateways installed"、"gateway is offline"、"credentials expired" 这类信息都是**第 4 层（语义模型刷新）**的问题，不是数据有问题。
2. **Refresh history 是第 4 层排错的入口。** Semantic model → `…` → Refresh history。Type 列只有两种值：
   - **On demand**：人手动触发（发布、点 Refresh now）
   - **Scheduled**：计划刷新自动跑
   > 如果 Scheduled 全失败、On demand 却能成功 → 问题在**计划刷新这条链路**（网关、凭据、时间窗口），不在数据或模型。
3. **刷新失败时按顺序问三个问题：**
   - 刷新历史里最后一次成功是什么时候？
   - 报错提到的是网关、凭据，还是数据源本身？
   - **同一个网关上的其他语义模型是不是也挂了？**（都挂 = 网关问题；只有这一个 = 这个模型的凭据或数据源问题）

## 3. RLS（Row-Level Security，行级安全）

### 是什么

**权限控制的粒度是"行"**，不是表、也不是列。同一张 `fact_sales`，华东销售看到 1,184 行，华北销售看到 532 行，销售总监看到 1,843 行——**同一个语义模型、同一份报表、同一个链接**，谁登录决定他属于哪个角色，角色决定他能看到哪些行。

可以理解成**一个由管理员设定、用户无法关闭的 WHERE 条件**，而且作用在引擎层，不在报表层：用户自己新建报表、或者用 Excel 连这个模型取数，一样受限。

> 与 `CALCULATE` 的关系：**RLS 先把数据收窄，`CALCULATE` 只能在剩下的范围里改筛选**，改不回被 RLS 挡掉的部分。

### 规则和人员名单是分开的

| | 存在哪 | 在哪配 |
|---|---|---|
| 角色的**规则**（DAX 筛选表达式） | `.pbix` 里，是模型的一部分 | **Desktop** → Modeling → Manage roles |
| **谁属于这个角色** | Service 里，是权限 | **Service** → 语义模型 → `…` → Security |

这是 RLS 最容易混的地方。

### ⭐ 规则要加在维度表上，不是事实表上

本次的角色 `华东区`：表选 `dim_customer`，表达式 `[region] = "华东"`。

**为什么**：筛选沿关系箭头流动（单向，维度 → 事实）。
- 加在 `dim_customer` 上 → 只剩 8 个华东客户 → **顺箭头**流到 `fact_sales`，成交自动收窄 ✅
- 加在 `fact_sales` 上 → 成交收窄了，但**逆箭头流不回去**，`dim_customer` 还是完整 14 行 → **报表的客户下拉框里仍会列出全部客户，信息泄露** ❌

**一条规则加在维度表上，整个模型跟着收窄。**

### ⭐ 验证：两个数字

| | Total Amount | Deal Count |
|---|---|---|
| 不加角色 | **27,106,012,244.79** | **1,843** |
| 以 `华东区` 查看 | **17,464,660,436.52** | **1,184** |

**而且没有任何提示说数据被过滤了。** 在真实场景里，华东的销售登录时连那条测试横幅都没有——他看到 17.4bn，并理所当然地认为那就是全部。

> **这就是排错清单里那句「"只有我看到的数不对" → 第 4–5 层的权限 / RLS 问题」的具体长相：不报错，只是数字变小、某些行消失、总计对不上。**

### ⭐ 坑一：开发者不受 RLS 限制

**工作区的管理员、成员，以及任何对语义模型有写权限的人，RLS 对他们不生效。**

设计上合理（开发者要能看到全量数据才能建模和排错），但会造成一个经典误会：

> 配好 RLS → 自己登录测试 → "看起来一切正常" → 上线 → 业务同事打开发现数字少了一大块。**你测的根本不是他们看到的那份。**

所以 RLS 只能用两种方式验证：
- Desktop 的 **View as**
- Service 的 **Test as role**（Security 页 → 角色右边 `…`）

> 顺带：`Test as role` **不需要先分配成员**，角色定义好就能测。分配成员是上线时的事。
> 另外，RLS 的成员必须是**组织目录（Entra ID）里的账号**；外部邮箱（如 gmail）要先作为来宾邀请进来才能分配。

### ⭐ 坑二：不属于任何角色的行会凭空消失

| region | 客户数 | 笔数 | 金额 |
|---|---|---|---|
| 华东 | 8 | 1,184 | 17,464,660,436.52 |
| 华北 | 4 | 532 | 7,669,571,162.90 |
| 华中 | 1 | 122 | 1,919,864,911.76 |
| **未知**（3 个孤儿 ID） | 1 | **5** | **51,915,733.61** |
| 合计 | 14 | **1,843** | **27,106,012,244.79** |

**三个区加起来 = 1,838 笔 / 27,054,096,511.18，比总额少 5 笔 / 51,915,733.61。**

漏掉的正是那 5 笔孤儿成交：它们指向 -1 未知客户，而未知客户的 `region` 是"未知"，**不属于任何一个区**。

危险在于：
1. 三个区域经理各看各的，**每个人的报表单独看都完全正常**。
2. 只有当有人把三份加总、和财务总账对比时，才会发现差了 5,192 万。
3. 这时第一反应往往是"数据丢了"，于是去查 Power Query、查 SQL、查源文件——**方向全错，根因在权限层。**

> **配 RLS 时必须专门问一句：有没有哪些行不属于任何一个角色？**
> 常见的有：孤儿记录、未分配的客户、新建还没归属的区域。做法是给"未知 / 未分配"单独建一个角色，或者保证总监角色不受限制，确保**总有人能看到全貌**。

## 4. 到岗第一周：打开别人的工作区先看什么

| 看什么 | 说明什么 |
|---|---|
| **工作区成员名单和角色** | 全组都是 Member = 所有人都能改生产报表 |
| 一个语义模型挂了几个报表 | 改模型的影响范围 |
| **Security 页有没有角色（Roles = 0）** | 没配 RLS，所有人看到的是全部数据 |
| **Refresh history** | 第 4 层排错入口；Scheduled 和 On demand 的成败模式 |
| 重要报表在不在 My Workspace 里 | 个人空间不能分享、不能发 App，没人能接手 |

### 两条习惯

1. **Service 里也能改模型**（网页版 Model view），但改了就和本地 `.pbix` 不一致。**以 `.pbix` 为准，改动在 Desktop 做完再发布。**
2. **删东西要按依赖顺序**：先删 Report，再删 Semantic model。先删模型会让报表变成孤儿。
   （同 SQL 里先删外键再删主表、合并前先清洗两边——都是依赖顺序问题。）

## 5. 附：这次顺带验证的一件事

项目文件夹从 `bhp-prep` 改名为 `iron-ore-reporting` 后，6 个查询的数据源路径全部失效。
**因为做了参数化，只改了 `DataFolder` 一个格子就全部修复；没参数化的话要改 6 处**，而且容易像 10-27 那样把文件名弄错、到后面某一步才报错。

> 参数化不防报错，它解决的是**出错之后要改几个地方**。

### 另一条：`.pbix` 能不能进公开仓库

`.pbix` 里装着**全部数据副本**，所以**提交 `.pbix` = 公开发布里面的数据**。
本项目是合成数据、README 开头已声明，所以没问题。
**到岗后的判断标准只有一句：这个 `.pbix` 里的数据能不能公开？不能就必须排除。**
