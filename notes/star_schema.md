# 星型模型笔记

> 陆怿行 · 2026-10-03 · 第 2 周产出物
> 用自己的话整理。面试被问到"什么是星型模型"时，照这份讲。

---

## 1. 事实表与维度表

**表的层面**

- **事实表**：记录发生过的事件，以及可以加总的数字。一行 = 一次事件。
- **维度表**：记录描述信息（谁、什么、在哪），用来筛选和分组。
- 判断方法：能 SUM 的是事实，用来 GROUP BY 的是维度。

本数据集：

| 类型 | 表 |
|---|---|
| 事实表 | `fact_sales`（成交）、`fact_index_price`（指数价格） |
| 维度表 | `dim_customer`、`dim_product`、`dim_port` |

表名前缀 `fact_` / `dim_` 就是约定俗成的命名方式，一看就知道是哪类表。一个星型模型里可以有多张事实表，共用同一批维度表。

**列的层面**（以 `fact_sales` 为例）

| 类型 | 列 |
|---|---|
| 度量（能加总） | tonnes_wet、amount_rmb、price_rmb_per_wmt、moisture_pct 等 |
| 外键（指向维度表） | customer_id、product_id、port_id |
| 直接放在事实表里的描述信息 | salesperson、sale_date |

`salesperson` 和 `sale_date` 是维度性质的信息，这份数据直接放进了事实表。更规范的设计会单独建 `dim_salesperson` 和日期表，事实表里只存编号。

## 2. 粒度（grain）

粒度回答的问题是：**事实表的一行 = 一个什么？**

`fact_sales` 的粒度：**一行 = 一笔成交，由 sale_id 唯一标识。**（D2 已验证 sale_id 无重复。）

建事实表、或者 JOIN 两张表之前，第一个问题永远是"这张表的一行是什么"。

---

## 3. 粒度不一致会导致什么错误

**加总时重复计算，而且 SQL 不会报错，很难发现数字错了。**

- **例一：同一张表里混了不同粒度。** 成交明细里有人粘进一行"3 月合计"。这一行的粒度是"一个月"，其他行是"一笔成交"，`SUM(amount_rmb)` 时 3 月的金额就会被算两遍。
- **例二：JOIN 不同粒度的表。** 销售目标表的粒度是"每个销售员每月一行"（比如王磊 3 月目标 5 亿）。直接 JOIN 成交明细的话，王磊 3 月有 30 笔成交，这 5 亿就被复制到 30 行上，`SUM(target)` 变成 150 亿。
  - 正确做法：先用 CTE 把成交汇总到"销售员 × 月"，**粒度对齐后再 JOIN**。

## 4. 代理键 vs 业务键

- **业务键**：业务里本来就有、有实际含义的标识。例如 `customer_name` = "华东特钢集团"、`sale_id` = `SH202601801`（编码了年份和序号）。
- **代理键**：系统生成、没有业务含义的编号。例如 `customer_id` = 101，101 本身不代表任何东西。

**类比**：James Bond 是业务键，007 是代理键。特工可能换化名、换身份，但军情六处始终用 007 追踪他，档案不会乱。

**为什么维度表的主键用代理键：**

1. **名字会变，编号不变。** 客户改名时，只需要改维度表的一行，不用去改事实表里的几千行。
2. **业务键不可靠。** 名字可能重复、写法可能不统一（比如"王磊"和"王磊 "），用干净的整数去 JOIN 更稳也更快。
3. **可以保留历史。** 客户从"贸易商"变成"钢厂"时，可以在维度表新加一行、分配新编号，旧成交仍指向旧的那一行，去年的报表不会被改写（缓慢变化维，SCD）。

原则：**事实表只存编号，描述信息只放在维度表里。**

## 5. 孤儿记录怎么处理

本数据中有 5 笔成交的 `customer_id` = 999 / 998 / 997，在 `dim_customer` 里找不到（D7 外键完整性检查发现）。

**规范做法：**

1. 在 `dim_customer` 里**新增一行**：专用编号（如 -1），`customer_name` = "未知客户"，`customer_type` = "未知"。
2. 在 `fact_sales` 里，把这 5 条记录的 `customer_id` **改成 -1**。事实表里不加名字，JOIN 之后自然显示"未知客户"。

```sql
-- 示意，不要在练习数据上直接跑（会永久修改表）
INSERT INTO dim_customer (customer_id, customer_name, customer_type)
VALUES (-1, '未知客户', '未知');

UPDATE fact_sales
SET customer_id = -1
WHERE customer_id IN (999, 998, 997);
```

**为什么比直接删掉好：**

- 直接删掉的话**总账会对不上**：这 5 笔共约 5192 万元（占总金额 0.19%，Q14）会从报表里悄悄消失，就像用 INNER JOIN 时少算的那部分。
- 之后**复查的难度也会增加**，没人知道曾经有过这些成交。
- 归入"未知客户"后，金额保留，报表上能清楚看到"有多少钱的成交不知道客户是谁"，方便有人去追查。

这类修正应该放在数据清洗层（Snowflake 的 STAGING 层）做，**原始数据保持不动**。
