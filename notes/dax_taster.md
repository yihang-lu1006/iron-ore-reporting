## 1. 计算列 vs 度量值

|  | 计算列 | 度量值 |
|---|---|---|
| 什么时候算 | **刷新时**算好，每行一个值，**存进表里** | **用户每看一次报表**时现场算 |
| SQL 类比 | `SELECT amount / tonnes AS price FROM …` | `SELECT SUM(amount) … WHERE … GROUP BY …`，而 WHERE 和 GROUP BY **由用户点哪里决定** |
| 用在哪 | 需要**按它分组或筛选**的东西（大单 / 中单 / 小单） | **所有汇总数字**：金额、笔数、占比、平均价 |
| 占空间 | 占，每行都存 | 不占，只存一个公式 |

> 一个度量值 = 一条写了聚合、但没写 WHERE 和 GROUP BY 的 SQL。

### 实验：两种算法算"平均单价"

```DAX
// 计算列：逐行算单价
unit_price_col = DIVIDE ( fact_sales[amount_rmb], fact_sales[tonnes_wet] )

// 度量值：先各自求和再相除 = 加权平均
Avg Price (weighted) = DIVIDE ( SUM ( fact_sales[amount_rmb] ), SUM ( fact_sales[tonnes_wet] ) )
```

| 年份 | `AVERAGE(计算列)` | 加权平均（度量值） | 差异方向 |
|---|---|---|---|
| 2025 | 891.33 | **890.41** | 加权更低 → 大单单价偏低（量大从优） |
| 2026 | 939.81 | **941.10** | 加权更高 → 大单单价反而偏高 |

**加权平均才对。** 计算列逐行先算好比率，汇总时只能做"平均数的平均数"，等于把 50,000 吨的大单和 1,000 吨的小单算得一样重。度量值是先把**可加**的金额和吨数各自加总，再相除。

每吨只差 1 块钱，但 2026 年卖了 1,165 万吨 → **按错口径算，金额差约 1,500 万元**，而且两种算法都不报错。

**结论：比率永远是度量值，不是计算列。** 实验后已把 `unit_price_col` 从模型中删掉——它占空间，而且同事把它拖进报表时默认显示 `Sum of` 或 Average，两个口径都是错的。**模型里只留对的东西。**

> `DIVIDE` 而不是 `/`：分母为 0 或空值时，`/` 报错或返回无穷大，`DIVIDE` 安全返回空值。DAX 里除法的标准写法。

## 2. 度量值引用度量值

先定义三块"积木"，其他度量值都引用它们：

```DAX
Total Amount = SUM ( fact_sales[amount_rmb] )
Total Tonnes = SUM ( fact_sales[tonnes_wet] )
Deal Count   = COUNTROWS ( fact_sales )

Avg Price (weighted) = DIVIDE ( [Total Amount], [Total Tonnes] )
```

**为什么：口径只定义一次。** 以后金额的口径要改（含不含税），只改 `Total Amount` 一处，所有引用它的度量值自动跟着变。同 Excel 里 SUMIFS 用 `$E$1` 参数格、Power Query 用 `DataFolder` 参数。

**写法约定：引用度量值只写 `[名字]`、不带表名；引用列一定写 `表[列]`。** 一眼能分清哪个是列、哪个是度量值。

**`COUNTROWS` vs `COUNT(列)`**：前者数行数（= `COUNT(*)`），后者数该列非空的个数。数"成交笔数"本意就是数行。

**验证（与 SQL / Excel 对账一致）**：钢厂 1,122 笔 / 16,463,184,095.41；贸易商 716 / 10,590,912,415.77；未知 5 / 51,915,733.61。
附带发现：**贸易商的加权单价最高**——可能因为单笔量小、要现货灵活性，愿付溢价。（假设，需验证；练习数据为模拟数据。）

## 3. CALCULATE

```DAX
Steel Amount = CALCULATE ( [Total Amount], dim_customer[customer_type] = "钢厂" )
```

按客户类型分三行时，**贸易商那一行显示的也是钢厂金额 16,463,184,095.41**。

| 行 | 这一行原本的筛选 | CALCULATE 做了什么 | 结果 |
|---|---|---|---|
| 钢厂 | `customer_type = 钢厂` | 替换成"钢厂" | 钢厂金额 |
| 贸易商 | `customer_type = 贸易商` | **同一列 → 被替换成"钢厂"** | 还是钢厂金额 |
| 未知 | `customer_type = 未知` | 同样被替换 | 还是钢厂金额 |

### ⭐ 规则：同一列的筛选被**替换**，其他列的筛选被**保留**

CALCULATE 只管它**点名**的那一列，没点名的一律不动。

所以如果同时按年份分组，`Steel Amount` 在 2025 和 2026 两行会是**不同**的数——年份在另一列，没被动过，算的是"当年的钢厂金额"。

SQL 类比：用户的 `WHERE customer_type = '贸易商' AND year = 2025`，被改写成
`WHERE customer_type = '钢厂' AND year = 2025`。**同列替换，其他列保留。**

## 4. ⭐ 双向筛选实验（这一节是模块 2b 的全部意义）

### 筛选方向复习

```
dim_customer（1）  ──▶  fact_sales（多）
   花名册                 成交流水
```

**箭头方向 = 筛选能流动的方向。** 单向 = 只能从维度表流向事实表。

- **顺箭头 ✅**：选 `customer_type = 钢厂` → `dim_customer` 剩 8 行 → 流到 `fact_sales` 剩 1,122 笔。
- **逆箭头 ❌**：选 `salesperson = 陈曦` → `fact_sales` 只剩他的单，但 **`dim_customer` 一行不少**。

> 类比：花名册和成交流水是两本册子。在花名册上圈"钢厂"，助手会去流水本里找出钢厂的单子；在流水本上圈"陈曦的单子"，助手**不会**反过来去花名册上划掉陈曦没服务过的客户。

### 4A 诱惑：一个明显错的数字

```DAX
Customer Count = COUNTROWS ( dim_customer )
```

按 `fact_sales[salesperson]` 分组 → **五个销售员全是 14**。
因为销售员的筛选在 `fact_sales` 上，逆着箭头流不到 `dim_customer`，花名册一行没少。

很自然的念头：**让筛选能倒流不就行了？**

### 4B 代价：一个隐蔽错的数字

只把 `fact_sales[customer_key] → dim_customer[customer_id]` 一条关系改成 **Both**（Power BI 自己弹出歧义警告），**完全没碰 `dim_product`**：

| 按矿种看 | 单向 | 双向 |
|---|---|---|
| `sales_amount` | 正常 | 没变 |
| `stock` | 正常 | 没变 |
| **客户数** | 全是 14 | **14 / 14 / 13 / 13 / 13 / 14 / 13** |

**筛选绕了一条路**：`dim_product` → `fact_sales` →（现在能倒流）→ `dim_customer`。

**这个"合理"的数字其实是错的。** 原始数据里 13 个正式客户**每一个都买过全部 7 个矿种**，所以本该都是 13。多出来的 1 来自 3 条孤儿成交（PB粉 有 998、PB块 有 997 和 999、麦克粉 有 999），这三个矿种多算了一个"未知客户"。

也就是说，这个数的真实含义是"买过该矿种的客户数 **＋ 该矿种有没有孤儿成交**"——**没有人会这样理解它。**

|  | 单向 | 双向 |
|---|---|---|
| 销售员客户数 | 14，**明显错**（五人一样），一眼看得出 | 正确 |
| 按矿种客户数 | 14，同样明显错 | **13 / 14，看起来非常合理** |

### ⭐ 结论：双向把一个显眼的错，换成了一个隐蔽的错

原来的 14 一看就不对，会有人来问；现在的 13 和 14 混在报表里，没人会怀疑，但口径已经不是任何人以为的那个意思了。

而且只改了**一条**关系，受影响的是**整个模型**（`dim_port` 也连着 `fact_sales`，按港口看客户数同样被间接筛）。关系多了还会出现**歧义路径**：Power BI 有时直接报错，有时不报错、自己挑一条路算，而你不知道它挑了哪条。

### 正解：不改模型，换度量值写法

```DAX
Customer Count (served) = DISTINCTCOUNT ( fact_sales[customer_key] )
```

直接数成交流水里出现过多少个不同的客户编号。不需要倒流——`salesperson` 和 `customer_key` 本来就在同一张表里。

结果：陈曦 13 / 张伟 13 / 刘洋 14 / 王磊 15 / 李静 14。

实验后已把关系**改回 Single**，并删掉误导人的 `Customer Count`。

### 两条带走的规则

1. **要数的东西在哪张表，就从哪张表去数。** 遇到"筛选流不过去"，先想**换个度量值写法**，不要改关系方向。改关系影响整个模型，换写法只影响这一个公式。
   （模块 4 会学 `CROSSFILTER`：在单个度量值里临时开双向，影响范围仅限那一个公式。）
2. **数客户、建关系一律用 `customer_key`**（孤儿已归到 -1）；`customer_id` 只在排查孤儿时用，否则 999 / 998 / 997 会被当成三个不同的客户。

> ⚠️ 遗留问题：王磊 15 比别人多，是因为 **-1"未知客户"也被算成了一个客户**。严格说不该算。模块 4 用 `CALCULATE` 加筛选条件排除——**又一次"数字看起来合理、口径却不符预期"**。写每个度量值时都要问一句：这个数到底包含了什么。

## 5. 到岗后用得上的

**打开别人的模型，先看 TMDL view 右侧的 Model 面板**（整个模型的目录）：

| 看什么 | 说明什么 |
|---|---|
| Tables / Relationships | 模型规模；关系数量对不对得上表的数量 |
| **Measures = 0** | 没有人定义过口径，所有数字都是字段区里拖出来的 `Sum of xxx` —— **坏味道** |
| **Roles = 0** | 没配 RLS，所有人看到的都是全部数据 |
| 关系里有没有 **Both** | 双向箭头是第一个要质疑的地方 |

**两个判断**：
- 报表里出现 `Sum of xxx` → 说明没人定义过这个指标的口径。
- 数字"看起来合理"不等于对 —— 口径错不会报错。对账是唯一的验证手段。
